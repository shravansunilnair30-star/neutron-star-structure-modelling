# Neutron Star Structure Modelling with the TOV Equations

**Project guide, results explanation, and copy-ready portfolio text**

## 1. The project in plain English

This project uses Python to calculate how a neutron star's pressure and enclosed mass change from its centre to its surface. A neutron star is so compact that Newtonian gravity is not sufficient; the model therefore uses the Tolman–Oppenheimer–Volkoff (TOV) equations, which describe hydrostatic equilibrium in general relativity.

The code starts with a chosen central pressure and integrates outward. When pressure falls to zero, that point is treated as the stellar surface. The enclosed mass and radius at that point form one point on a mass–radius curve. Repeating the calculation for different central pressures produces a sequence of model stars.

The central scientific idea is that the predicted mass and radius depend on the equation of state (EOS): the relationship between matter's pressure and energy density.

## 2. What the equations mean

The TOV equations used by the project are

\[
\frac{dm}{dr}=4\pi r^2\frac{\epsilon}{c^2}
\]

\[
\frac{dP}{dr}=-\frac{G(\epsilon+P)\left(m+4\pi r^3P/c^2\right)}
{c^2r^2\left(1-2Gm/(rc^2)\right)}.
\]

- \(r\): distance from the centre of the star.
- \(m(r)\): gravitational mass enclosed within radius \(r\).
- \(P(r)\): pressure at radius \(r\).
- \(\epsilon(r)\): total energy density.
- \(G\): gravitational constant.
- \(c\): speed of light.

The first equation accumulates mass as the integration moves outward. The second describes how pressure decreases outward to support the star against gravity. Its extra relativistic factors distinguish it from the Newtonian hydrostatic-equilibrium equation.

The models assume a static, spherical, non-rotating star with isotropic pressure. Real neutron stars can rotate, and their interiors are uncertain; these models do not include every possible physical effect.

## 3. What an equation of state does

An EOS tells the solver how pressure relates to energy density or matter density. The starter model uses a simple polytropic EOS:

\[
P=K\rho_0^\Gamma,\qquad
\epsilon=\rho_0c^2+\frac{P}{\Gamma-1}.
\]

Here \(K\) sets the pressure scale, \(\Gamma\) controls how stiffly pressure rises with density, and \(\rho_0\) is the rest-mass density. This model is useful for learning the numerical method, but it is not a complete microscopic description of neutron-star matter.

The project also contains a piecewise-polytropic approximation calibrated to the SLy EOS literature. “Piecewise” means that different density ranges use different polytropic relations. A low-density crust prescription is matched onto the higher-density segments. This is still an analytic approximation; it is not the same thing as loading the original tabulated SLy4 data.

## 4. Files and what each one is for

- `neutron_star_tov.py` — the educational single-polytrope TOV solver.
- `neutron_star_sly.py` — the SLy literature-calibrated piecewise-polytropic approximation.
- `convergence_check.py` and `sly_convergence_check.py` — numerical sensitivity checks for the corresponding solvers.
- `physical_validation.py` — checks sound-speed causality for the analytic SLy approximation, compares selected global properties with rounded published CompOSE reference values, and tests sensitivity to solver settings.
- `neutron_star_compose.py` — separate solver intended to read the official tabulated CompOSE RG(SLY4) EOS.
- `compose_convergence_check.py` — planned convergence workflow for the table-driven solver.
- `technical_report.md` — the detailed technical report.
- `PHYSICAL_VALIDATION_STATUS.md` — a short status record distinguishing completed checks from pending work.
- `outputs/` — CSV files, summaries, and plots generated by the scripts.
- `neutron_star_presentation.pptx` — slide presentation.

## 5. Completed results: analytic SLy approximation

The executed `physical_validation.py` checks produced the following results for the analytic SLy piecewise-polytropic approximation with a matched low-density crust:

| Quantity | Model result | Rounded CompOSE RG(SLY4) reference | Relative difference |
|---|---:|---:|---:|
| Maximum-mass causal-boundary model mass | 2.0462668 solar masses | 2.06 solar masses | -0.667% |
| Radius at that model | 9.982195 km | 10.02 km | -0.377% |
| Radius at 1.4 solar masses, interpolated | 11.754450 km | 11.7 km | +0.465% |

The analytic EOS reaches the sound-speed limit \(c_s=c\) at approximately \(2.008568\times10^{15}\,\mathrm{g\,cm^{-3}}\). The reported causal-boundary solution is kept just below that limit; its maximum interior \(c_s^2/c^2\) is 0.9999999702.

The convergence study varied the ODE solver tolerance and maximum radial step across four configurations. The largest observed changes were approximately \(8.01\times10^{-7}\%\) in mass and \(2.46\times10^{-5}\%\) in radius, both below the project's 0.1% numerical-stability tolerance.

### How to interpret these numbers

These results support the conclusion that the tested causal branch of the analytic SLy approximation is numerically stable under the tested settings and gives global properties close to the rounded values listed by CompOSE for RG(SLY4).

They do **not** prove an exact reproduction of the original tabulated EOS. The analytic fit and crust prescription are not identical to the CompOSE table, so the comparison is a cross-model consistency check rather than a same-EOS validation. The very small numerical changes show solver stability for the tested settings; they do not remove uncertainty from the EOS approximation itself.

## 6. What is not finished yet

The table-driven route is **not yet end-to-end validated**. The scripts `neutron_star_compose.py` and `compose_convergence_check.py` have not been run against the actual official `eos.thermo` and `eos.nb` files in this environment.

To finish that stage:

1. Download the cold, beta-equilibrated RG(SLY4) EOS from the official CompOSE page: https://compose.obspm.fr/eos/134
2. Extract `eos.thermo` and `eos.nb` into a `data/` folder next to the Python scripts.
3. Install the dependencies with `pip install -r requirements.txt`.
4. Run `python neutron_star_compose.py --data-dir data`.
5. Run `python compose_convergence_check.py`.
6. Inspect the generated causality diagnostics, low-pressure surface treatment, convergence summary, and mass–radius curve comparison with the official `eos.mr` reference.
7. Only then update the report to state what passed or failed.

Until these steps are complete, do not describe the project as a fully validated tabulated-SLy4 implementation.

## 7. How to run the completed checks

Use Python 3.10 or later in a terminal from the project folder:

```bash
python -m venv .venv
```

Windows:

```bash
.venv\Scripts\activate
```

macOS/Linux:

```bash
source .venv/bin/activate
```

Then:

```bash
pip install -r requirements.txt
python neutron_star_tov.py
python neutron_star_sly.py
python physical_validation.py
```

The scripts save generated results in `outputs/`. Run the CompOSE scripts only after adding the official data files as described above.

## 11. A simple way to explain the project in an interview

**What did you build?**  
I built a numerical model that integrates the relativistic hydrostatic-equilibrium equations from the centre of a neutron star to its surface, then repeats this for different central pressures to create a mass–radius curve.

**Why use the TOV equations?**  
Neutron stars are compact enough that general-relativistic effects matter, so Newtonian hydrostatic equilibrium is not adequate.

**What is the EOS?**  
It describes how pressure and energy density are related inside the star. Different EOS choices can produce different mass–radius curves.

**How did you check the model?**  
For the analytic SLy approximation, I checked that the sound speed did not exceed the speed of light along the reported causal branch, varied numerical solver settings, and compared selected mass–radius indicators with rounded CompOSE reference values.

**What is the main limitation?**  
The analytic SLy approximation is not identical to the official tabulated SLy4 EOS. The separate solver for the official table still needs to be run with the actual CompOSE data files before claiming tabulated-EOS validation.

**What would you do next?**  
Run the table-driven solver on the official EOS data, inspect its causality and interpolation behaviour, test convergence and surface treatment, and compare the resulting mass–radius curve with the official reference sequence.
